## What this is

`bore` — async Rust TCP/UDP tunnel/proxy/transfer (`#![forbid(unsafe_code)]`). Exposes a local port through a remote server, bypassing NAT/firewalls. Ships `bore_cli` lib + `bore` binary.

**Six subcommands:** `bore local <port>` (public tunnel: server assigns public port → local `<port>`); `bore proxy` (secret consumer: connect named provider → relay to local port); `bore server` (relay server); `bore transfer listener|sender` (file transfer: resume, BLAKE3 verify, parallel streams); `bore test-udp` (NAT/UDP diag; `--tcp-secret-id` → two-peer latency/bandwidth test); `bore vpn listen|connect` (Linux L3 VPN, `--features vpn`, root/CAP_NET_ADMIN). Plus `bore vhost` (subdomain reverse proxy) and `bore hash-password` (argon2id line, `--features ssh-gateway`).

**Core transport:**
- One long-lived yamux-muxed TCP conn per tunnel (control port 7835); plain TCP or TLS (`https://` URL).
- Public: server opens data substreams → client splices to local. Secret: consumer opens substreams → server relays to provider → provider splices to local.
- `--carriers N`: N parallel TCP conns, round-robin per proxied conn (HOL + cwnd isolation).
- `--udp`: UDP hole-punch + QUIC direct for secret tunnels (each proxied conn = own QUIC bidi stream); auto-fallback to relay.
- `--udp` for PUBLIC `bore local` (no `--tcp-secret-id`): server→client QUIC direct, **no STUN/hole-punch** (server public, client dials it — same as `bore vhost --udp`). Client opens N (`--carriers`) QUIC conns to server `--vhost-quic-port`; server round-robins inbound across them (own `PublicDirectEntry`/`DirectPool` per tunnel), writes `mux::STREAM_READY`, splices; per-conn fallback to warm TCP relay. Needs `bore server --udp`.

- Relay path AEAD-opaque: server splices ciphertext, never plaintext IP packets.
- **Never `tokio::io::split` a `mux::Stream` across two tasks.** `yamux::Stream` keeps a single parked-task waker on its internal channel (`poll_read` + `poll_write` both call `sender.poll_ready`); two tasks overwrite each other's waker → loser never woken → stream wedges silently under load. CRITICAL: per-datagram RR across carriers reordered a single flow → tunnelled TCP read the reorder as loss → `--carriers 4` could HALVE throughput / explode UDP loss to 25-44% (netns+netem). NEVER restore per-datagram RR on the direct path. `n==1` → idx 0, byte-identical. RELAY keeps per-datagram RR (reliable streams; replay window sized for it, DEC-10) — do not flow-pin it without resizing the window. A single bulk flow gains nothing from carriers (one carrier); the real VPN bottleneck is the single inner TCP flow (Mathis) — parallelise the workload. `--carriers` default stays 1; rarely helps a VPN (see docs/vpn/VPN_BANDWIDTH_ASSESSMENT.md).
- VPN 1:1 uplink uses `send_batch_wait` (BACKPRESSURE, BW-F3): on a full QUIC datagram send buffer it AWAITS room instead of quinn silently dropping the OLDEST queued datagram — drop = congestion the tunnelled TCP reads as loss (cwnd collapse) + bufferbloat. Awaiting pauses the TUN read → kernel TUN queue backpressures the inner senders. ONLY the dedicated 1:1 uplink task may block here; the SHARED hub router keeps non-blocking `send_batch` (a blocking peer would HOL every other peer). Relay branch ignores backpressure (bounded channel already blocks).

Kernel SILENTLY clamps `SO_SNDBUF`/`SO_RCVBUF` to `net.core.{w,r}mem_max` (stock Ubuntu/AWS 208 KiB → ~10 MB/s at 20ms RTT regardless of Quinn windows, CPU idle). `configure_udp_socket_buffers` (holepunch.rs, Linux) forces past it with `SO_{SND,RCV}BUFFORCE` (nix `*BufForce`, needs CAP_NET_ADMIN which VPN has) → falls back to clamped setter on EPERM → getsockopt-verifies + `warn!`s remediation when a clamp survives (was a silent `debug!`). Requested 16 MiB (Fix #1).
- **Direct-path UDP punch sockets must NEVER set `SO_REUSEADDR`** (`holepunch::bind_socket`, holepunch.rs). Two wildcard UDP sockets that BOTH set `SO_REUSEADDR` co-bind the same `0.0.0.0:port` → kernel delivers inbound to the **last binder**. So when two direct-path tunnels (VPN + secret, vhost, public `--udp`) share a `--nat-udp-preferred-port` on one host — even in **separate processes** — each ~30s re-punch rebinds the port and **steals** the other's inbound QUIC, idle-closing the live conn → establish→die→re-punch ~30s LOCKSTEP FLAP (both flap; only-with-concurrent-secret repro). FIX: bind the preferred port WITHOUT `SO_REUSEADDR`; kernel then refuses the 2nd binder (`EADDRINUSE`) → `bind_socket` falls back to ephemeral port + `warn!` (1st tunnel keeps the firewall-friendly port; 2nd gets its own, still punches or stays on relay). UDP has no TIME_WAIT → same-tunnel `--auto-reconnect` still rebinds the fixed port, but callers MUST drop the old socket BEFORE binding the new (no overlap), else rebind hits `EADDRINUSE` → downgrades to ephemeral. Regression: `bind_socket_*` unit tests + `T-STRESS-PORTCLASH`/`T-STRESS-MIX` in `vpn_netns_test.sh`. Mechanism proof: `docs/plans/udp_flap/`. Direct QUIC layer (keepalive 3s / idle 10s, transport_config) byte-identical since `3a5c87b` — flap was NEVER the QUIC layer; do not re-bisect it.

For tests/benchmarks needing a fixed MTU. Default off = dynamic auto-tune (`pmtu_monitor` resize path). `pmtu_monitor(.., pin)` carries the flag.
- VPN direct path: a `TooLarge` datagram send is a per-packet DROP, never link death. TUN MTU runs ahead of the QUIC path MTU right after every direct switch → full-size packets exceed `max_datagram_size()` until the PMTU monitor narrows the TUN. `DirectConn::send_datagram` returns typed `DatagramSend::{Sent,TooLarge}` (NOT a stringly error — quinn's `Display` for `SendDatagramError::TooLarge` is `"datagram too large"`, so substring-matching `"TooLarge"` silently never fired + killed the link). `send_batch` returns the drop count; only genuine link death returns `Err`. PMTU monitor shrinks immediately on one below-current sample (`pmtu_shrink_now`, fast recovery), grows only on 3 stable samples (`pmtu_decision`, anti-flap). Black-hole hysteresis (Fix #2): a grow then shrink back within 30s marks the grown size as a ceiling (`pmtu_decision`'s `ceiling` arg blocks GROWING into it again — shrinks never blocked) → TUN stops chasing quinn's doomed re-probe of an MTU the WAN path can't carry (the ~70s 1162↔1414 oscillation + periodic `TooLarge` drop bursts). Ceiling clears after 5 min of a stable MTU → a genuinely improved path is rediscovered.
- VPN direct-path candidates must NEVER include an address routed into the TUN. A peer candidate inside a locally-tunneled subnet (`peer_routes`, e.g. connector routes `10.10.0.0/19 → bore0`, peer offers `10.10.16.138`) makes the QUIC handshake loop through the relay: it succeeds, bridge switches to direct + drops relay halves, then the looped path dies at the QUIC idle timeout (`read_datagram: timed out` ~10s; provider sees peer as *overlay* IP `10.99.x.x`). `filter_tunneled_candidates` drops these before punching → fall back to relay, never a fake-direct path that silently dies. Conservative by design (drops even if a more-specific connected route would reach it off-tunnel).
- VPN direct upgrade is NOT one-shot: `direct_upgrade_task` retries on a fixed 30s grid (`DIRECT_RETRY_INTERVAL`, `should_retry_direct`) while on relay → a link that came up on a UDP-hostile network upgrades to direct in-place (no reconnect) once the path opens. Relay stays stable through every failed attempt. Stops on success or upgrade-channel close. Both peers stay aligned: grid anchored at pairing, interval > worst-case attempt (`DIRECT_PUNCH_WAIT` 15s). Server broker MUST re-arm per round (reset deadline + clear `punched` on each repeated `UdpCandidateOffer`) or retries never re-punch, AND clear the listener's stored candidates right after each punch (else round N+1 re-punches round N's dead socket → connector times out against a closed port). `--relay-only` skips it entirely. Also: netns harness (`vpn_netns_test.sh`) refuses to run against a release binary older than `src/` — rebuild `cargo build --release --features vpn` (as your user, not root) before `sudo`-running it.

## VPN multi-client (hub-and-spoke, `--max-clients N>1`) — `mod hub` in `vpn.rs` + `vpn_server.rs`

- I-MC1: `--max-clients 1` (default) byte-for-byte the legacy 1:1 path. Hub mode = SEPARATE early branch (`run_listen_hub`); never edit the 1:1 path to add hub behavior. Hub requires server pool addressing (no static /30); connector `--advertise` rejected by server (D4).

Connector→server bytes UNCHANGED (I-MC2).

- Each peer derives its OWN keys from its OWN `session_nonce` (passed RAW, UDP_NONCE_LEN bytes — never padded/resized, else HKDF inputs diverge + AEAD keys won't match) with its OWN shared nonce counter (I-MC4 — never shared across peers).

Also changed the 1:1 connector default: existing netns site-to-host tests pass `--accept-all-routes`.

## VPN FORWARD default-deny gap (`--forward-accept`)

- On a **default-deny FORWARD** host (Docker daemon `-P FORWARD DROP`, ufw, hardened) a gateway reaches ONLY itself; every host BEHIND it is stranded. bore's nft NAT rules live in a SEPARATE table and **cannot override a terminal FORWARD `DROP`** from another chain (accept not terminal across base chains; drop is). Docker DAEMON's rule persists on the host even when bore runs natively (not in a container) — `docker0`/`br-*` in `ip route` is the tell.
- `--forward-accept` (gateway/listen side) punches an `ACCEPT` for the tun↔LAN pair into the iptables `filter` FORWARD chain via per-link custom chain `bore_<id>_fwd` (F3/F4 pattern: `-N` + `-I FORWARD -j` at TOP + two `-A ... ACCEPT`), torn down by id alone (SIGKILL `stale_reclaim` safe). **iptables, NOT nft** — the real-world deny lives in `ip filter FORWARD` regardless of bore's NAT backend; a hand-rolled `nft inet filter forward` policy-drop is NOT covered (out of scope, v1). Off (default) ⇒ bore PROBES `iptables -S FORWARD` + `warn!`s exact remediation when policy is DROP/REJECT (`forward_policy_is_deny`). Detection-vs-install mutually exclusive (no probe when punching). RAII-reverted. Covered by T-FWD in `vpn_netns_test.sh` + `apply_*` unit tests.
- NOTE: `--forward-accept` only fixes the FORWARD hop. NAT'd (`real@virtual`) subnets ALSO need `--nat-masquerade` for the return path when the gateway is not the LAN router (I-NAT5) — orthogonal; the field repro needed BOTH.

## SSH ingress gateway (`--ssh-gateway`, feature `ssh-gateway`, branch `ssh`, IMPLEMENTED 2026-07-04 — Phases 1-7 done, `docs/SSH_GATEWAY.md` §6 is the operational guide)

Embeds a `russh` server in `bore server` so a stock OpenSSH client (`ssh -R`/`-L`, no `bore` binary) can create public/vhost/secret tunnels. Ingress-only: from the accepted SSH channel inward, reuses the existing registries/relay/admin/weblog/`--max-conns` data path unmodified.

- **D1 (naming heuristic, `parse_forward_spec`, `src/sshgw.rs`):** bare numeric port ⇒ public; bare label + port 80/443 ⇒ vhost; bare label + port 0 ⇒ secret provider; any other bare-label port ambiguous + rejected. `vhost/<label>`/`secret/<id>` prefixes in the bind address override the heuristic, any port. `direct-tcpip` (`-L`) to `<id>`/`secret/<id>` is always a secret consumer (port is an ignored nonzero placeholder — OpenSSH's `-L` CLI rejects a literal `0`, unlike `-R`).
- **SSH leg = TCP relay only, never UDP/carriers.** No `--udp`/QUIC direct, no `--carriers>1`, no hole-punch flags on the SSH leg — native-bore-client-only; a client naming one via `exec`/env gets an explicit warning (I-SSH2), never silent drop. A native client + an SSH client can coexist on the same tunnel namespace, even the same demuxed port simultaneously.
- **I-SSH1:** `--ssh-gateway` off (or feature compiled out) ⇒ the control-port accept path is BYTE-IDENTICAL to before this feature existed — confirmed by `git diff` showing zero removed lines in the legacy accept loop (`src/server.rs`), not just "no visible bugs".
- **I-SSH2:** every client-transport-only parameter named via `exec`/`SetEnv`/authorized-keys options gets an explicit warning line, never silently ignored or misapplied.
- **I-SSH3:** keepalive 20s / reaper 60s in parity with the native secret-tunnel zombie-entry invariant — no ghost admin rows. A REAL netfilter half-open (not a process kill) exposed a genuine bug: the vhost/secret finalize task's own strong `Arc<ConnState>` clone (held for the task's entire `pending()`-forever lifetime) created a reference cycle that kept `Drop for ConnState` (which aborts every task in `self.forwards`) from ever firing on an ungraceful death. Fixed with explicit `drop(state)` before each `pending()` tail in `src/sshgw.rs` — found+verified by `scripts/ssh_gateway_test.sh`'s T-SSH-N1, which cargo tests structurally cannot reproduce (no real network stack to netfilter-DROP). SAME reference-cycle shape (`state` captured for `await_params`/`queue_message`, never used again, then a long-lived tail future) existed in the PUBLIC-tunnel `tcpip_forward` task too — missed first pass because its tail is `run_public_forward`'s real accept loop, not a `pending()`. Symptom: Ctrl+C on an `ssh -R <port>:...` client left the bound listener (+ admin row) alive forever → next reuse of that port failed to bind. Fixed the same way (`drop(state)` right after last use, before the accept loop). Whenever a NEW `tcpip_forward_*`/exec-consuming task is added, it needs the same explicit `drop(state)` if `state` is unused past setup and the task tail outlives the connection — the compiler will NOT drop it early (lexical scope, not liveness, governs async drop timing here).
- **I-SSH4:** `mux::LinkOpener::Ssh`/`SshOpener::open` never writes the yamux `STREAM_READY` marker byte — SSH has no equivalent framing; the caller IP travels as the channel-open request's own originator-IP field instead.
- **I-SSH5 (D-SSH2):** same-identity takeover — a new SSH session authed with the SAME identity (authorized-keys comment, or password label) as the incumbent holder of a vhost label/secret id evicts + replaces it (deterministic `autossh` reconnection); a DIFFERENT identity, or a name held by a *native* (non-SSH) tunnel, is always rejected — SSH identities and the HMAC secret are different trust domains, never mixed.
- **I-SSH6 (`shell_request` must never force-close, bug-hunt 2026-07-05):** a bare `ssh -R`/`-L` (no `-N`, no `exec` — the ordinary invocation) still gets OpenSSH's *default* behavior of ALSO requesting an interactive shell on the session channel. The gateway used to deny it with `exit_status(1)` + `eof` + `close`; OpenSSH treats its "primary session" exiting nonzero as reason to disconnect the WHOLE connection, tearing down every active `-R`/`-L` forward on it — real report: a bare `-R secret/id:0:localhost:8080` got "interactive shells are not supported" and the just-granted forward died with it. Fixed by NEVER closing this channel with a nonzero exit from `shell_request` — held open instead (this is what makes I-SSH7 possible). Deliberately does NOT special-case "zero forwards yet" into a hard rejection: a secret *consumer* (`-L <port>:secret/<id>:1`) has no `tcpip-forward`-equivalent to announce itself in advance — the server only learns of it when a real proxied conn opens a `direct-tcpip` channel, which can be well after the shell request fires. Closing for "nothing YET" would silently reintroduce the bug for a consumer whose first connection hasn't happened. Only a best-effort, NON-closing informational line (`NO_FORWARD_YET_MESSAGE`) printed when nothing is known (`ConnState::has_forwards`/`has_secret_consumers` both empty) — never destructive.
- **I-SSH7 (tunnel info banner, same bug-hunt):** once a vhost/public/secret-provider/secret-consumer forward finishes establishing, the gateway writes a short professional English status report to the session channel (`vhost_info_banner`/`public_info_banner`/`secret_provider_info_banner`/`secret_consumer_info_banner` + `ConnState::deliver`, all `src/sshgw.rs`) — the actual payoff of the fix above, not a side effect. **Never** reports the client's own `-R`/`-L` local host:port: RFC4254's `tcpip-forward`/`direct-tcpip` have no field for it — pure client-local state the server can't know, guessing would mislead in the one place a user checks for truth. Delivery via `Handle::data(channel_id, ..)` — works from any task holding a cloned `Handle`, no `Session`/dispatch-loop access needed — essential because a forward's *final* state (bound port, cert-missing https downgrade, resolved headers) isn't known until well after `channel_open_session` already fired + did its one-shot drain (crosses `PARAMS_GRACE`). `ConnState::session_channel` (set by `channel_open_session`, ordered BEFORE its drain so a racing `deliver` can't fall in the gap) lets `deliver` target the channel directly instead of only queueing. Secret-provider banner includes the exact consumer command with `<same-host>`/`<same-port>` placeholders (never a GUESSED hostname); `--ssh-advertise-address HOST` + `--ssh-advertise-port PORT` (env `BORE_SSH_ADVERTISE_ADDRESS`/`BORE_SSH_ADVERTISE_PORT`, 2026-07-08) let the OPERATOR declare the public endpoint (a front proxy rewrites the port + SSH has no Host/SNI, so the server can't derive it) → command prints ready-to-copy; the two flags independent, whichever unset keeps its placeholder (zero-regression default). Unit: `secret_provider_banner_consumer_command_advertise`. Related: NO_FORWARD_YET_MESSAGE explicitly notes the `-L` secret-consumer case is normal (forward activates on the first local connection — server can't see a `-L` earlier; `-T` only skips the PTY, session+shell request still happens → that message expected even with `-T`). - **I-SSH8 (inapplicable params must warn, real report 2026-07-05):** `https=on force-https=on` on a VHOST forward (HTTPS there governed server-side by `--vhost-mode`, never per-tunnel) was silently swallowed — `parse_params`'s own `warnings` can't catch this class (built generically, before the caller knows which forward TYPE the exec string applies to). - **Control-port demux (D8, Phase 6):** with the gateway enabled, `sshgw::demux_pre_tls` peeks the first byte (2s timeout — a real SSH client waits for the server's own banner + sends nothing first, sslh-style) and 3-way classifies: `Ssh` (timeout or `b'S'`) → gateway; `Tls` (0x16) → configured TLS acceptor, then a second 4-byte peek (`demux_post_tls`) checks for a literal `SSH-` prefix (SSH-over-TLS via `ProxyCommand openssl s_client`, D4); anything else (`Direct`: HTTP/bore) routes STRAIGHT to `route_connection`, BYPASSING any configured TLS acceptor — this is what lets a plain HTTP/bore client keep working on a port that also serves TLS. `SshGateway::serve_connection` generic over `mux::Transport` → runs identically over `TcpStream`, `Prefixed<TcpStream>`, a `TlsStream`.
- **I-SSH9 (ALPN-first post-TLS demux — the browser-preconnect misroute, field bug 2026-07-06):** inside TLS, "silence ⇒ SSH" ALONE is WRONG: a browser's speculative/pool HTTPS conns (preconnect, spare sockets for parallel assets) complete the TLS handshake then idle PAST the 2s `SSH_PEEK_TIMEOUT` before their first request — the old post-TLS fallback handed them to russh, whose `SSH-2.0-russh_…` banner rendered as the page body, and the poisoned sockets sat in the browser pool (requests stuck `pending`, missing assets, refresh not healing). - **I-SSH10 (bounded channel-open + wedged-session eviction, resilience hunt 2026-07-06):** RFC 4254 has no deadline for a CHANNEL_OPEN reply → a wedged-but-TCP-alive OpenSSH client (frozen process/suspended laptop: kernel ACKs+answers nothing; or zero-window peer jamming the session loop in `flush_into`, where keepalives are never even SENT so `keepalive_max` reaping is blind) left every proxied conn `pending` FOREVER holding its `--max-conns` permit — field symptom: stalled pages only a manual ssh-client restart healed.
