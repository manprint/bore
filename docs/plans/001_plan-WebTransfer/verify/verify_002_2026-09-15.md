### V002-F02 — `T-WEB-DOWNLOAD-RELAY` fails on WebKit: the gate is red
- **Status:** `FIXED` — 2026-09-15 by `execute verify V002-C1`; every download leg now runs on a persistent profile and asserts the capability, and `npm run test:e2e` reads 54 passed / 0 failed across chromium, firefox and webkit.
- **Severity:** `BLOCKER`
- **Category:** failing-gate
- **Where:** `web/transfer/tests/e2e/download.spec.mjs:89` — plan ref `phase_04.md § 3.4` Done criterion
- **Expected:** "`T-WEB-DOWNLOAD-RELAY` passa su Chromium/Firefox/WebKit con adapter OPFS reale **o fixture esplicitamente separata dove WebKit headless manca supporto**."
- **Actual:** `npm run test:e2e` → `1 failed, 51 passed`; `[webkit] › download-relay › click verifies exact bytes, then saves explicitly` gets `{ error: "UNSUPPORTED" }` instead of `{ pending: true }`. Measured cause: in Playwright's default (ephemeral) WebKit context `navigator.storage.getDirectory` **exists** and then throws `UnknownError: The operation failed for an unknown transient reason`, so `repository.supported()` returns false. In `webkit.launchPersistentContext(...)` the same call succeeds and a positional `createWritable`/`getFile` round trip returns the right bytes — so this is a context-profile property, not a missing engine feature. Neither branch of the plan's alternative is implemented: the test uses the ephemeral context and there is no separated fixture.
- **Impact:** the phase-3 gate cannot be green, and the one engine whose OPFS behaviour is most likely to diverge in production has no real coverage of the download path.
- **Correction:** give the download spec a persistent browser context (all engines, so the three legs stay identical), and assert the capability probe rather than letting a false `supported()` surface as a wrong return value.

### V002-F03 — The OPFS sink is quadratic: measured 8.4 MiB/s at 128 MiB against 22.8 MiB/s at 32 MiB
- **Status:** `FIXED` — 2026-09-15 by `execute verify V002-C2`; re-measured on the same loopback path, 32 MiB 1403 -> 898 ms (22.81 -> 35.63 MiB/s) and 128 MiB 15182 -> 2580 ms (8.43 -> 49.61 MiB/s). Throughput now RISES with size, which is what says the quadratic term is gone.
- **Severity:** `MAJOR`
- **Category:** efficiency
- **Where:** `web/transfer/src/storage.js:231` (`writeChunk`) — plan ref `phase_04.md § 3.4` ("commit di bytes+digest+RLE in ordine crash-safe (flush OPFS, poi transazione IDB)"), `overview.md` I-WEB8
- **Expected:** a bounded, linear receive path; the plan's durability step is a **flush**, not a rewrite.
- **Actual:** every chunk opens `handle.createWritable({ keepExistingData: true })`, which in all three engines materialises a swap file by **copying the whole existing output**, so writing chunk *i* costs *i* MiB. Measured end to end through the real relay on loopback (Chromium, one file, this tree): 32 MiB → 1403 ms (22.81 MiB/s); 128 MiB → 15182 ms (8.43 MiB/s) — 4× the payload for 10.8× the time. Isolated in-browser benchmark, 128 × 1 MiB writes:

  | strategy | chromium | firefox | webkit |
  |----------|---------:|--------:|-------:|
  | `createWritable({keepExistingData:true})` per chunk (today) | 7318 ms | 4374 ms | 5678 ms |
  | one part file per chunk | 219 ms | 1294 ms | 159 ms |
  | …plus a single concatenation pass | 512 ms | 1522 ms | 388 ms |

  `createSyncAccessHandle` — the API that would give a real in-place `flush()` — is not callable on the main thread in any of the three engines (`TypeError: fh.createSyncAccessHandle is not a function`), so the fix cannot simply swap the call.
- **Impact:** the plan's own target file size is 1 TiB per offer. At 128 MiB the recipient already spends more time copying its own partial than receiving it, and the cost grows with the square of the transfer.
- **Correction:** stage each verified chunk as its own generated part file (linear, durable on `close()`) and hand the finished download out as a `Blob` composed of those parts in order. C2 below carries the measurement that settled the design: composing costs 9–17 ms for 128 parts and no extra bytes, so no assembly pass — and no interrupted-assembly recovery — is needed.

### V002-F04 — The receiver cannot consume a stream that skips resumed chunks
- **Status:** `FIXED` — 2026-09-15 by `execute verify V002-C3`; `receiver_places_chunks_by_plan_when_the_source_skips_verified_ranges` drives a source that sends only the missing chunks and reads the exact file back. Red-checked: restoring the linear index fails it.
- **Severity:** `MAJOR`
- **Category:** divergent
- **Where:** `web/transfer/src/receiver.js:359` and `:429` — plan ref `phase_04.md § 3.4` ("Al resume … inviare massimo 4096 range"), `phase_04.md § 3.5` (`T-WEB-CANCEL-RESUME`)
- **Expected:** the recipient sends its verified ranges and then receives only the missing chunks, writing each at its own offset.
- **Actual:** `transfer.chunkIndex` starts at 0 and advances by one per completed chunk, so the *n*-th chunk that arrives is always written at offset `n × 1 MiB` and compared against `entry.chunks[n]`; `acceptFinal` additionally requires `receivedBytes === entry.size`. Both are only true when nothing was skipped. The receiver already asks for a skip (`body.resume` is populated from its verified ranges), so the two halves of the feature contradict each other. It is masked today only because the server does not forward the descriptor to the source (`STATE.md` §8 row 54) and `sender.js:479` therefore always plans a full send.
- **Impact:** the moment 3.5 wires the resume descriptor through — which is the phase's own next step — every resumed download fails on the first chunk-digest comparison. The defect is invisible to every test in the tree because no test exercises a skipping sender.
- **Correction:** derive the expected chunk order in the receiver from its own verified ranges (`planSend(chunkCount, verifiedRanges).send`), index writes and digest comparisons through that list, and check FINAL against the bytes that were actually meant to travel; add a unit test with a skipping sender.

### V002-F07 — The resume record is re-read and the database re-opened on every chunk
- **Status:** `FIXED` — 2026-09-15 by `execute verify V002-C5`; one connection per repository (`storage_opens_the_database_once_for_many_operations`) and the record carried in memory.
- **Severity:** `MINOR`
- **Category:** efficiency
- **Where:** `web/transfer/src/storage.js:157` (`db()`), `:177` (`withStore`), `web/transfer/src/receiver.js:399` — plan ref `overview.md` I-WEB8
- **Expected:** bounded, proportionate bookkeeping beside the data path.
- **Actual:** `withStore` calls `db()` — a fresh `indexedDB.open` — and closes the connection for **every** operation, and `acceptData` performs a `loadRecord` before each `saveRecord` purely to carry the accumulated `chunkDigests` forward. That is three connection cycles per chunk over state the receiver already holds in memory. Measured for 128 chunks: 41 ms (chromium), 587 ms (firefox), 426 ms (webkit).
- **Impact:** small next to F03 but on the same hot path, and it is the reason Firefox's bookkeeping costs more than half a second per 128 MiB.
- **Correction:** keep one open connection per repository instance and carry the record in memory, writing it (not reading it back) after each verified chunk.

### V002-F08 — The file-picker save path fetches a `blob:` URL the page's own CSP forbids
- **Status:** `FIXED` — 2026-09-15 by `execute verify V002-C2`; the staged `Blob` travels on the staged entry and is written straight to the picker handle. No code fetches an object URL.
- **Severity:** `MAJOR`
- **Category:** divergent
- **Where:** `web/transfer/src/main.js:292` (`stagedFileOf`) — plan ref `phase_04.md § 3.4` ("`showSaveFilePicker` può apparire solo come enhancement rilevato a runtime")
- **Expected:** where `showSaveFilePicker` exists, the verified file is written through it; the anchor is the fallback.
- **Actual:** that branch obtains the bytes with `await fetch(staged.url)` over the object URL, and the page is served with `Content-Security-Policy: … connect-src 'self'` (`src/web_transfer_http.rs:42`), which refuses a `blob:` fetch. Measured in all three engines on the real room page: a `fetch` of an object URL fails (`TypeError: Failed to fetch` / `NetworkError` / `Load failed`). The branch catches the error and silently falls through to the anchor, so the enhancement never writes through the picker it just opened. No test covers it — headless Chromium does not expose `showSaveFilePicker`, so the e2e always takes the anchor path.
- **Impact:** on a real Chrome or Edge the user picks a destination, and the file is then delivered by the fallback instead — or, had the fallthrough not existed, not at all.
- **Correction:** keep the staged `Blob` on the staged entry and write it to the picker handle directly; never fetch an object URL from a page whose own CSP forbids it.
