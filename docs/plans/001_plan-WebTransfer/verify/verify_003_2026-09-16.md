The functional direct-to-relay recovery works in the automated tests. It does
not explain or solve the reported 400 MB Linux Chrome ↔ Android Chrome/Brave
case: ~4 MB/s direct, followed by a relay at ~15–20 MB/s, with both devices on
one Wi-Fi network and the Bore server on an AWS `t4g.micro`. The existing native
`bore transfer` saturates the user's link, according to the user's comparison.
The exact cause of the phone's fallback is **unknown** because the browser's
selected ICE path and failure timeline are not retained. Neither the Wi-Fi nor
the AWS instance has been established as its cause.

## Field log interpretation (server output supplied by the user)

- At 20:21 UTC the server started its STUN responders on UDP 7835 and its shared
  QUIC endpoint on UDP 443. This proves those listeners started, not that the
  two browsers used a particular ICE candidate pair. The vhost QUIC carrier
  established seconds later belongs to the native vhost transport, not to the
  browser's direct WebRTC DataChannel.
- The `--udp-memory-budget=512` / `--max-carriers=1024` warnings describe the
  native QUIC server endpoint's 32-slot admission and 1 MiB stream window.
  Browser-to-browser WebRTC direct does not use those QUIC windows or that
  server data endpoint. A possible indirect memory/CPU effect on relay traffic
  cannot be inferred without RSS, CPU and per-transfer measurements.
- The `web-transfer pre-auth refused ... class="denied"` lines around 20:38,
  20:50 and 20:51 UTC occur **before** a browser joins a room. Source review
  shows this class means an absent room, a mismatched member token, or an
  unusable room lock; the log intentionally does not distinguish them. It is
  not a WebRTC failure or a direct-to-relay event. The log has no per-attempt
  ICE state, selected pair, `direct_failed` reason or transfer timing, so it
  cannot identify the reported fallback.
- Two different public client addresses appear near each other at 20:31 and
  20:37 UTC. The log does not bind either to a browser or transfer, so this is
  **not proof** the phone used cellular data. If they are the two test peers,
  the server saw different internet egress paths despite the intended shared
  Wi-Fi; confirm the address/device mapping and selected ICE pair before
  treating the test as a LAN path.

## Findings

### V003-F01 — Direct throughput collapse persists without a two-host acceptance measurement

- **Status:** `OPEN` — characterised, gate delivered, **field run outstanding**
  (`execute verify V003-C1`, 2026-09-17). Three of the four things C1 asked for are
  done; the fourth needs a second host.
  - **The unsupported assertion is gone, and it is gone because it was falsified,**
    not because it was rephrased. Instrumented with C3's trace read after EACH
    repetition (the store keeps eight attempts, so reading it at the end dropped the
    slow one and numbered the survivors by store index — the first instrumented run
    published five fast repetitions that way), the collapse is **ONE `waitLow` of
    1.3–1.7 s**. Not the queue depth: at 512 KiB/128 KiB the peak queue is 1.17 MB
    instead of 4.5 MB and one wait in seven still takes 1654 ms while the other six
    total 47 ms. Not the ICE path: `host/host` on every repetition, fast and slow.
    Not send discards: `packetsDiscardedOnSend` reads 1209 on a fast repetition and
    38 on the slowest. And **not loss on the path**, which is the one that settles
    it — firefox over the SAME loopback never collapses (6/6 at 26.40–35.56 MiB/s,
    longest wait 155 ms, `direct / relay` 0.882x). Two engines, one path, one of
    them stalls.
  - **What it is instead:** a chromium DataChannel send-path freeze, at most once
    per transfer. The one-second-class duration suggests an SCTP RTO or zero-window
    probe inside the engine and is written as a HYPOTHESIS, because chromium exposes
    no `sctp-transport` statistics (`cwnd`, `rwnd`, `unackData` read `?` in every
    trace). Recorded as a measured browser limit in `docs/transfer/WEB_TRANSFER_PERF.md`
    §4.6 and `phase_05.md`.
  - **The gate exists:** `T-WEB-PERF-LAN` — `scripts/perf/web_transfer_lan.sh` plus
    `web/transfer/tests/perf/lan.perf.mjs`. It serves the room over HTTPS on the LAN
    address (the server refuses plaintext off loopback, and without a secure context
    the page has no `crypto.subtle`, OPFS or `RTCPeerConnection`), creates it with the
    shipped `bore transfer web`, drives only the SOURCE — a phone cannot be driven by
    Playwright, and the completion instant is still the recipient's, because it
    acknowledges only verified ranges — selects the arm by removing
    `RTCPeerConnection` from the source so the recipient needs no flag, asserts
    `pathCommits`, prints every raw sample and states `goal=50.00MiB/s … verdict=`.
    Proved end to end on both arms with a stand-in recipient (direct 3.71 MiB/s with
    one 2087 ms wait, relay 69.57 MiB/s) — which is the harness working, not a result.
  - **Why it stays open:** the measurement this finding asks for is two hosts, a
    400 MB file and the reporter's network. That cannot be produced from a machine
    with one host, and a loopback number must never be published in its place.
- **Severity:** `MAJOR`
- **Category:** untested
- **Where:** `docs/plans/001_plan-WebTransfer/phase_05.md:527`, `docs/transfer/WEB_TRANSFER_PERF.md:500`, `STATE.md` §9 — D21/D22, phase 4.4/4.6, `T-WEB-PERF-DIRECT`.
- **Expected:** D21/D22 prioritise an efficient direct peer path; 4.6 measures direct against relay and §9 says a two-host measurement is still needed.
- **Actual:** current Chromium loopback, 8 MiB ×6, verified path commits: direct `[56.50, 10.01, 57.97, 45.82, 2.36, 4.56]` MiB/s against relay `[67.11, 73.39, 76.78, 69.26, 80.24, 69.87]`; median paired ratio `0.399`. The slowest direct run spent `3309/3385 ms` in sender `src.drain`, while sealing took about 12 ms and staging about 30–42 ms. At 32 MiB ×3, direct `[59.99, 9.80, 29.33]` against relay `[77.39, 77.59, 88.47]` MiB/s, with up to 3082 ms in `src.drain`. The user's ~4 MB/s is within this reproduced low mode. Phase 4.4 uses browser contexts on one host; no shipped gate runs Chrome/Android across real Wi-Fi at 400 MB. The performance document calls SCTP packet loss/RTO the cause, but there is no ICE/SCTP packet or `getStats()` evidence proving that mechanism.
- **Impact:** the measured direct path can be much slower than relay even before the phone's later fallback. A green functional gate does not establish the requested throughput.
- **Correction:** instrument the direct path as in C3, benchmark a 400 MB file on two real hosts with the user's browsers and the same AWS server, alternate direct/relay runs, compare the native transfer on the same topology, then fix the measured bottleneck. Keep the RFC/browser transport diagnosis a hypothesis until the trace supports it.

### V003-F02 — A stalled DataChannel can keep growing its send queue

- **Status:** `FIXED` (`execute verify V003-C2`, 2026-09-17) — the drain deadline now
  fails the attempt with the fixed wire reason `timeout` and REJECTS the wait with an
  `AbortError`, which the sender already reads as "this attempt was abandoned": it stops
  reading the file and waits for the relay attempt, which resumes from the recipient's
  verified ranges. Resolving survives for the one case it is right for — the queue really
  did fall below the mark and only the engine's event was missed. The deadline is
  injectable (`drainTimeoutMs`) because a gate on a ten-second deadline cannot take ten
  seconds. Gate `stalled_channel_never_queues_after_drain_deadline`, red-checked: with the
  old unconditional resolve it fails (queue grows, no failure reported). The e2e resume
  path the timeout reuses is `T-WEB-DIRECT-FALLBACK`'s (same `direct_failed` + ranges +
  fresh relay attempt); a real stalled queue cannot be produced on loopback, so the
  discriminating gate is the unit and this is stated rather than implied.
- **Severity:** `MAJOR`
- **Category:** divergent
- **Where:** `web/transfer/src/webrtc.js:552`, `web/transfer/src/sender.js:299`, `docs/plans/001_plan-WebTransfer/phase_05.md:103,135,497` — I-WEB8 and phase 4.2/4.6.
- **Expected:** sender waits above 4 MiB until the channel drains to 1 MiB; queues are bounded, and a stalled path falls back.
- **Actual:** `waitLow()`'s 10 s timer calls `finish()` and **resolves** even when `bufferedAmount` remains above 4 MiB. `sendArchive()` then enqueues the next 1 MiB chunk. Repeated timeouts can add more chunks to an undrained browser queue. The unit test checks the drain event and abort, but never the 10 s timeout while still above high water. The phase's “next send decides” statement is inconsistent with its bounded-queue invariant: an open channel can accept further sends without having drained.
- **Impact:** on a stalled direct path, tab memory and latency can grow until the browser rejects a send; this can contribute to the observed slow-then-fallback shape, but has **not** been identified as the cause of this phone run.
- **Correction:** on drain timeout, fail that direct attempt with an existing fixed reason (`timeout`), reject the wait, and let the normal relay resume path run. Add a fake-clock test that leaves `bufferedAmount` above high water and proves no additional file read/send after the timeout, one failure report, and successful relay continuation.

### V003-F03 — The implementation cannot identify why an established direct path fell back

- **Status:** `FIXED` (`execute verify V003-C3`, 2026-09-17) — the page keeps a bounded,
  redacted trace per direct attempt: the fixed reason, the ICE/channel timeline in
  milliseconds, the **type** of the selected candidate pair plus the numeric `getStats()`
  counters (RTT, congestion window, bytes/messages) and the drain accounting; it is
  exposed only through `Copia diagnostica percorso`, and the server writes one `info!`
  line per ACCEPTED `transfer.direct_failed` carrying the fixed reason and the opaque
  ids only. Redaction is by ALLOW-LIST in `web/transfer/src/diagnostics.js`, which is why
  the gates can assert that every string in the report is either an opaque id or a short
  enumeration. Gates: `T-WEB-DIRECT-DIAG` (chromium/firefox/webkit), the four units in
  `web/transfer/tests/unit/diagnostics.test.mjs`, and `t_web_log_privacy`; red-checked by
  copying an address into the summary, by removing the drain accounting, by re-dropping
  the log line. The correction's other half — a real Android Wi-Fi run — is a
  MEASUREMENT and is tracked with F01/C1; the instrument it needed now exists.
- **Severity:** `MAJOR`
- **Category:** untested
- **Where:** `web/transfer/src/webrtc.js:317-355`, `web/transfer/src/main.js:385-412`, `src/web_transfer_http.rs:1630-1660`, `web/transfer/tests/e2e/direct.spec.mjs:280` — phase 6.2 observability, I-WEB15.
- **Expected:** enough privacy-safe evidence to distinguish path failure from congestion or an application send failure.
- **Actual:** `iceConnectionState`/`connectionState` failure, a `disconnected` lasting 2 s, channel close/error, and failed `send()` all abandon direct; the server immediately starts a new relay attempt. There is no `getStats()` call or selected candidate-pair type, byte/loss/RTT, DataChannel queue, timestamped state timeline or diagnostic export. `recordDirect()` writes only to a test-only hook. The server accepts the fixed failure reason but does not log a useful path-failure event. The end-to-end fallback test forcibly closes the channel; native UDP same-LAN tests do not exercise browser ICE or Android Wi-Fi. The W3C specification calls `disconnected` transient and describes using `getStats()` to decide whether an ICE restart is appropriate; the fixed 2 s policy is implemented as planned, but unvalidated for this network.
- **Field evidence:** the supplied AWS log shows STUN/QUIC listeners and several coarse `class="denied"` room-auth refusals, but no WebRTC path or failure event. `src/web_transfer_http.rs:870-925` places those refusals before room admission; `src/web_transfer.rs:2682-2702` narrows their meaning to absent room, token mismatch or a poisoned lock.
- **Impact:** the user's specific “why direct → relay?” cannot be answered from present data. The selected path might have been local `host` or a server-reflexive path; “same Wi-Fi” alone does not identify it.
- **Correction:** retain a bounded, privacy-safe per-attempt trace before closing the peer connection: fixed reason, elapsed times and state transitions, selected pair *types* (`host`/`srflx`) and numeric `getStats()` counters, queue high-water duration, and first/last verified byte. Expose an opt-in copyable diagnostic and a structured server failure event keyed only by opaque IDs. Never include IP/port, candidate strings, SDP, room secrets, filenames or payload. Add a test that verifies both diagnostic distinctions and redaction, then run a real Android Wi-Fi transition/recovery case. Reassess the 2 s grace and ICE-restart policy from that trace.

### V003-F05 — The receiving browser discards the remote ICE end-of-candidates marker

- **Status:** `FIXED` (`execute verify V003-C5`, 2026-09-17) — `handleSignal` now hands the
  marker to the ICE agent with `pc.addIceCandidate(null)`, exactly once, after every
  candidate that preceded it; a marker that arrives before the remote description waits in
  ONE dedicated slot that does not consume the 128-candidate budget, and duplicates are
  ignored. The wrong comment and the unit assertion that the marker "adds nothing" are
  gone. Gates: `remote_end_of_candidates_is_applied_after_queued_candidates` (red-checked:
  re-dropping the marker fails it) and a host-only real-browser negotiation on
  chromium/firefox/webkit, which reads the delivery out of the C3 trace
  (`remote-candidates-done`) and asserts no `srflx` candidate exists to hide a missing
  marker behind.
- **Severity:** `MAJOR`
- **Category:** divergent
- **Where:** `web/transfer/src/webrtc.js:470-475`, `web/transfer/tests/unit/webrtc.test.mjs:270-271` — phase_05.md §4.2, R1/R4.
- **Expected:** trickle candidates and the final marker are delivered to the remote ICE agent. [WebRTC 1.0](https://www.w3.org/TR/webrtc/) specifies that an end-of-candidates indication is passed to `addIceCandidate()`; `null` denotes the end for all media descriptions.
- **Actual:** the local browser emits `rtc.ice {candidate:null}` and the server forwards it, but the receiving `handleSignal()` returns immediately without calling `pc.addIceCandidate(null)`. The unit test explicitly asserts that the marker “adds nothing”. The comment claims the browser can learn the remote end from its *own* gathering state, which is a different state.
- **Impact:** remote ICE never receives the explicit end marker. This can affect negotiation completion or failure timing on some network/browser combinations. It does **not** by itself explain a later fallback after a channel was already open.
- **Correction:** deliver the marker after remote description and after queued candidates, remembering at most one pending marker if it arrives early. Preserve the 128-candidate cap and idempotence. Test the call order and a host-only real-browser negotiation in all three engines.

### V003-F04 — README troubleshooting gives incorrect LAN/STUN and speed explanations

- **Status:** `FIXED` (`execute verify V003-C4`, 2026-09-17). Both rows named ONE
  cause as certain where the measurement says otherwise, and both sent the reader to
  change a setting instead of looking at the path. The LAN row now says what is
  actually true on one subnet — the browsers pair on their **host** candidates, STUN
  is not involved, so `--web-transfer-no-stun` is not what forces the relay there;
  what forces it is UDP not crossing between the two machines (client isolation on
  the access point, a host firewall, different subnets) — and the first step is now
  `Copia diagnostica percorso`, which names the candidate-pair TYPE that carried the
  bytes. STUN is named only for the case it governs, two DIFFERENT networks. The
  speed row is split in two: `relay`, where the shipped throttle is already
  100 MiB/s and both legs cross the server (so the bound is usually the WAN, and the
  value in force is on `/admin/api/v1/config`), and `diretto`, which did not exist
  before although the direct path is measurably bimodal — it names the 1.3–1.7 s
  freeze V003-C1 measured, points at `drain_longest` in the report, and says plainly
  that there is no setting to change. Gate: `t_web_readme`, seven needles on the new
  wording and two on the old wording that must be GONE (a reader who finds the wrong
  row first stops reading), red-checked — restoring the old LAN row fails the gate
  and names the string. Needles are single lines because the windows runner checks
  the tree out with CRLF (B-A016).
- **Severity:** `MINOR`
- **Category:** divergent
- **Where:** `README.md:2628-2631` — phase 4.5/6.6, R4.
- **Expected:** troubleshooting describes the deployed ICE and performance behaviour accurately.
- **Actual:** the row for two machines on one LAN treats `--web-transfer-no-stun` as a cause of relay, although this setting leaves ICE `host` candidates available and those can connect on the LAN. The slow-download row covers only relay and its rate limit; direct was already documented as bimodal at 2–14 MiB/s. The shipped default relay cap is 100 MiB/s, so a 15–20 MB/s relay is not explained by that default alone.
- **Impact:** operators may change STUN or the relay cap while overlooking the actual selected path or the direct queue stall.
- **Correction:** describe `no-stun` as host-only, distinguish host reachability/AP isolation from STUN reachability, add direct slowdown and AWS relay-route diagnostics, and avoid naming one unmeasured cause as certain.
